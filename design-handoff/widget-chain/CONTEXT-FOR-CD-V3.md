# 위젯 체인 UI v3 — 도킹 레인 (사용자 모델 확정) 재설계 의뢰 (writer → CD)

_2026-10-08 · writer · **멘탈 모델이 사용자 확정됨** — 이번엔 방향 탐색이 아니라 확정 모델의 설계입니다._

## 0. 두 번의 어긋남과 이번 확정 — 반드시 먼저 읽기

- v1(바+위젯 내 토글): "위젯 **간**이 아니라 위젯 안" 이라 기각.
- v2(커넥터 오버레이): 위젯 간으로 갔지만 **"시스템이 정한 고정 파이프라인"** 전제가 어긋남.
- 사용자 원문 (2026-10-08): **"체인은 빈 상태가 디폴트고, 그 안에 원하는 위젯을 드래그해서 각자 원하는 체인을 만들 수 있게."**
- 모델 분기 질문에 사용자가 **A. 도킹 레인**을 직접 선택 (아래 목업이 사용자가 보고 고른 그것 — 이 구도가 SSOT):

```
┌─ 체인 1 ─────────────────── 단계별 승인 ▾ ─┐
│  ┌──────────┐    ┌──────────┐   ┌╌╌╌╌╌┐    │
│  │ 인터뷰     │───▶│ 전사록    │──▶┆  +  ┆   │
│  │ 어시스턴트 │    │ 생성기    │   ┆빈 슬롯┆   │
│  └──────────┘    └──────────┘   └╌╌╌╌╌┘    │
└────────────────────────────────────────────┘
캔버스(남은 카드): [데스크 리서치] [가이드라인] [AI UT] …
```

**확정 의미론**: 체인 = 캔버스 위의 **선반(레인)**, 빈 상태로 생성 · **카드 본체가 레인 안으로 이동해 도킹** · 해체 시 카드 원위치 복귀 · 작업 화면과 체인 구조가 한 몸(도킹된 카드에서 평소처럼 작업).

## 1. writer 확정 가정 (설계 전제)

1. **호환 가드**: 드롭 가능한 쌍 = 데이터가 실제로 이어지는 쌍만(백엔드 어댑터 존재 엣지). 현재 = 프로빙→전사→인터뷰분석(→탑라인). 안 되는 조합은 드롭 거부 + 사유 표시 — 이 거부 모먼트의 시각 언어도 설계 대상.
2. 1차 드래그 대상 = 위 계열 위젯. 비호환 위젯은 드래그 시작은 되되 레인이 받지 않음(또는 시작부터 비활성 — CD 판단).
3. 탑라인 보고서는 카드가 아니라 인사이트 분석기의 산출물 — v2 의 **산출물 노드**(레인 끝)를 승계.
4. 모드(단계별 승인 기본/자동)·크레딧 사전 고지·ChainView 계약 — 전부 불변. 승인 모먼트는 **레인 안 카드 사이** (v2 캡슐 문법 승계 — 이제 카드가 인접하므로 v2 의 거터·다중 행 문제가 소멸).

## 3. CD 설계 질문 (v3 의 열린 문제)

1. **빈 체인 생성 진입점** — 어디서 "새 체인"이 생기나 (캔버스 툴바 버튼? 빈 공간 인터랙션? 위젯을 위젯에 겹치면 자동 생성?). 빈 레인(슬롯만 있는 선반)의 모습 포함.
2. **도킹/언도킹 제스처** — 카드를 레인 슬롯에 끌어넣기/빼기, 유효·무효 드롭의 피드백, 순서 재배열.
3. **레인과 캔버스 배치의 공존** — 레인 자체의 위치(이동 가능?), 도킹으로 빠진 자리의 처리, 해체 시 복귀 모션.
4. **실행 중 상태** — 도킹 카드 축소/실물 크기? 실행 중 레인 헤더(모드·진행 n/m·종료) 구성.
5. 다중 체인 동시 존재(레인 2개+)의 표현 — 1차에서 제한한다면 그 제한의 표시.
