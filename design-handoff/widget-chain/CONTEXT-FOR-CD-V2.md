# 위젯 체인 UI v2 — 3방향 프로토타입 비교 의뢰 (writer → CD)

_2026-10-08 · writer · 탐색 의뢰 — 승자 선정 전이므로 **풀 번들 아님**, 비교용 컴프만._

## 0. 왜 v2 인가 — 사용자 피드백 (원문)

> "아 체인 ui 는 내가 의도한 거랑 조금 다른데? 저렇게 **위젯 내에 들어가는 게 아니라 '위젯 간'의 체인**을 생각했던 거야."

v1(09-widget-chain 번들)의 Q1·Q2 결정 — 상단 체인 바 + 카드 칩 + 위젯 내 진입 토글 — 은 **비인접 제약**(체인 위젯 사이에 통역 카드가 끼어 있어 카드 간 커넥터가 성립 안 함) 위에서 합리적이었습니다. 사용자 의도는 그 제약을 깨더라도 **연결 자체가 카드 사이에 시각적 실체로 존재**하는 것입니다. v1 구현(PR #1329)은 머지 보류 중 — 백엔드·계약(ChainView)·칩·i18n 은 유효하며 프레젠테이션 방향만 다시 정합니다.

## 1. 의뢰 — 3방향 각각 UI 프로토타입

**사용자가 세 방향을 눈으로 보고 고릅니다.** 각 방향당 같은 장면을 그려 1:1 비교가 되게 해 주세요.

### 방향 ① 체인 레인 — 재배열 + 실 커넥터
- 체인 활성 시 묶인 카드들이 **한 줄(레인)로 모이고**, 카드 사이에 **실제 커넥터 세그먼트**.
- 커넥터가 상태를 산다: running = 흐름 펄스 · awaiting = 커넥터 중간 **승인 캡슐**("다음: 인터뷰 분석 💎25 → [진행] [건너뛰기]") · error/paused = 커넥터 단절 표기.
- 설계 과제: 비체인 카드 처리(밀림/dim) · 체인 종료 시 **원 배치 복원 규칙** · 사용자 수동 배치(발행 레이아웃)와의 공존.

### 방향 ② 커넥터 오버레이 — 배치 불변 + 엣지
- 카드는 제자리, **SVG 엣지**가 카드→카드를 잇는다(노드 에디터 문법). 비체인 카드는 체인 활성 시 dim.
- 승인 캡슐은 엣지 중점(또는 도착 카드 접점)에.
- 설계 과제: 비인접 구간의 **긴 엣지 라우팅·가독성**(v1 기각 사유가 부분 잔존 — 이걸 디자인으로 어디까지 눌 수 있는지가 이 방향의 시험).

### 방향 ③ 포트 연결 — 드래그로 잇는 생성
- 카드에 **출력 포트(산출물)·입력 포트**가 노출되고, 사용자가 포트를 끌어 다음 위젯에 놓으면 체인 생성. 연결 후 모습은 ①или② 와 결합 가능.
- "위젯 간 체인"의 가장 문자적 구현 — 생성 UX 까지 '사이'로 옮기는 안. 프로토타입은 **생성 제스처 장면 + 연결 완료 장면** 두 컷이면 충분.

## 2. 각 방향이 공통으로 보여줄 장면 (비교 최소 세트 — 풀 상태 매트릭스 아님)

| # | 장면 | 왜 |
|---|---|---|
| S1 | 체인 활성 · 2단계 진행 중 (프로빙 done → 전사 running) | 연결·흐름의 기본 모습 |
| S2 | **승인 대기** (전사 done → 인터뷰 분석 awaiting, 💎 비용 노출) | 이 기능의 핵심 모먼트가 '사이'에서 어떻게 생겼나 |
| S3 | 비체인 카드 공존 (통역 카드가 체인에 안 묶인 채 캔버스에 있음) | 비인접 제약을 각 방향이 어떻게 푸는지 |

캔버스 맥락은 v1 C0 의 미니카드 구도 재사용 가능. 상태 전수(바9·칩6 등)는 **승자 선정 후 풀 번들에서** — 지금은 방향 비교가 목적.

## 3. 불변 조건

- 데이터 계약 = v1 그대로: `CONTEXT-FOR-CD.md` §3 `ChainView` + `WRITER-ANSWERS.md`. **계약 변경 없이 그릴 수 있어야** 백엔드(이미 프로덕션 머지된 A·B·C·E)가 그대로 삽니다. 계약으로 부족하면 proposed-prop 으로.
- 모드 2종(단계별 승인 기본 · 자동 opt-in)·크레딧 사전 고지 원칙 불변.
- 상단 체인 바는 **전역 요약으로 격하 또는 제거** — 방향별로 CD 판단(각 컴프에 처리안 표기).
- v1 자산(칩·노드 문법·톤 체계) 재사용 자유 — 단 "위젯 안에 산다" 는 요소(진입 토글 위치 포함)는 재배치 검토 대상.
